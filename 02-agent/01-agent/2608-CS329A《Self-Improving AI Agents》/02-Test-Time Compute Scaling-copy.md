## 二、为什么要扩展测试时计算

传统提升模型能力的主要方式是：

1. 扩大预训练数据和参数规模；
2. 进行 SFT、RLHF 等后训练；
3. 在推理阶段只生成一次答案。

第三点存在明显浪费：同一个模型针对同一道题，不同采样可能产生完全不同的推理路径。一次回答错误，并不一定意味着模型没有解决问题的能力，可能只是没有采样到正确轨迹。

因此，可以把推理过程从：

> 输入 → 生成一次 → 输出

扩展为：

> 输入 → 生成多个候选 → 评价/验证 → 选择或融合 → 输出

这就是 Test-Time Compute Scaling。

## 三、Large Language Monkeys：重复采样

最简单的推理扩展方法是 Repeated Sampling：

1. 对同一道题重复调用模型；
2. 生成 $K$ 个候选答案；
3. 使用验证器找到正确答案；
4. 输出通过验证的候选。

如果模型单次生成正确答案的概率为 $p$，并近似假设各次采样相互独立，那么至少一次成功的概率为：

$$
\operatorname{pass@k}=1-(1-p)^k
$$

即使 $p$ 很小，增加采样次数也可能显著提高问题覆盖率。

例如，《Large Language Monkeys》在 SWE-bench Lite 上将 DeepSeek-Coder-V2-Instruct 从单次采样的 15.9% 提升到 250 次采样下的 56%，超过当时 43% 的单次采样最佳结果。[论文](https://arxiv.org/abs/2407.21787)

这说明：

> 小模型内部可能已经存在解决问题的能力，只是单次采样不容易将这种能力暴露出来。

### Coverage 不等于实际准确率

这里必须区分：

- **pass@k / coverage**：$K$ 个候选中只要存在一个正确答案就算成功；
- **实际 pass@1**：系统能否从候选中真正选择出正确答案。

前者近似假设拥有 Oracle Verifier；后者才是用户最终获得的效果。两者之间的差距就是后面讲到的生成—验证鸿沟。

## 四、推理阶段为什么会出现幂律

对于一道固定问题，失败概率会随采样次数呈指数下降：

$$
P(\text{全部失败})=(1-p)^k
$$

但把许多难度不同的问题聚合起来，整体覆盖率往往呈现幂律扩展。

关键原因是问题的单次成功率 $p_i$ 呈长尾分布：

- 简单问题的 $p_i$ 很高，少量采样就能解决；
- 中等问题需要几十次采样；
- 少数极难问题的 $p_i$ 极低，可能几千次才偶尔成功；
- 这些极难问题主导了大采样预算下的整体曲线。

因此：

> 单个问题是指数扩展，问题集合经过长尾难度分布聚合后，可以表现为幂律扩展。

这也意味着，可以使用少量采样估计扩展曲线，预测达到某个覆盖率所需要的推理预算。[“Large Language Monkeys”扩展规律论文](https://arxiv.org/abs/2502.17578)

## 五、真正的瓶颈：生成—验证鸿沟

重复采样只有在“正确答案能够被识别”时才有用。

### 容易验证的领域

- 数学：答案匹配、符号计算、形式化证明；
- 代码：编译、单元测试、静态分析；
- CUDA Kernel：正确性测试和性能测试；
- 游戏与仿真：环境奖励；
- 结构化任务：规则检查、约束检查。

这些领域可以建立客观、自动、低成本的反馈，因此适合持续自我改进。

### 难以验证的领域

- 开放式研究；
- 创意写作；
- 商业分析；
- 长文本综合；
- 主观质量判断；
- 缺乏标准答案的 Agent 任务。

这些任务即使生成了正确候选，也可能因为验证器不可靠而选不出来。

论文实验发现，在缺乏可靠验证器的任务上，多数投票和 Reward Model 在采样数达到几百后会趋于饱和，无法继续获得接近 pass@k 的收益。[Large Language Monkeys](https://arxiv.org/abs/2407.21787)

所以，本讲最重要的判断是：

> 随着模型生成能力增强，系统瓶颈正在从 Generator 转向 Verifier。

## 六、推理计算的两种扩展方向

### 1. 横向扩展：Parallel Sampling

独立生成多个候选：

$$
x \rightarrow \{y_1,y_2,\ldots,y_k\}
$$

优点：

- 高度并行；
- 增加候选多样性；
- 适合存在明确验证器的任务。

缺点：

- Token 成本高；
- 候选可能高度相似；
- 必须有可靠选择机制。

### 2. 纵向扩展：Sequential Revision

模型连续修改同一个答案：

$$
y_0 \rightarrow y_1 \rightarrow y_2 \rightarrow \cdots
$$

典型动作包括：

- 检查推理；
- 查找错误；
- 根据反馈修正；
- 回退到先前步骤；
- 尝试替代方案。

它更接近 reasoning model 或 Agent 的迭代过程，但可能陷入错误方向或出现“越改越差”。

实践中通常将二者结合：

> 多路并行探索 + 每一路有限深度修正 + 最终验证和融合。

## 七、Outcome Reward Model 与 Process Reward Model

| 类型 | 评价对象 | 优点 | 局限 |
|---|---|---|---|
| Outcome Reward Model，ORM | 最终答案 | 标注和使用相对简单 | 无法定位中间推理错误 |
| Process Reward Model，PRM | 每个推理步骤 | 可以引导搜索、提前剪枝 | 步骤标注昂贵，错误可能累积 |
| Rule-based Verifier | 规则、测试、约束 | 客观、稳定 | 只适用于可形式化任务 |
| LLM Judge | 内容整体质量 | 适用范围广 | 存在偏差、自洽错误和位置偏差 |

PRM 可以与 Beam Search 或 Tree Search 结合：

1. 生成多个下一步；
2. 为每个步骤打分；
3. 保留高分分支；
4. 淘汰低分分支；
5. 重复直到产生完整答案。

相比在最后从大量完整答案中选择，这种方式能把计算集中在更有希望的推理路径上。

## 八、计算预算应根据问题难度动态分配

测试时计算不是越多越好，也不应该平均分给所有问题。

课程介绍的研究发现：

- 简单问题：一次或少量采样已经足够；
- 中等问题：增加采样或搜索收益最大；
- 极难问题：小模型可能几乎没有成功概率，继续采样只是浪费计算；
- 不同难度问题适合不同的“并行宽度 × 推理深度”。

因此，需要 Compute-Optimal 策略：

1. 估计问题难度；
2. 判断当前模型是否有非零且足够的成功概率；
3. 为可解决但困难的问题增加计算；
4. 对简单问题提前停止；
5. 对当前模型基本无法解决的问题切换更大模型或放弃。

相关研究显示，这种按问题自适应分配预算的方法，相比固定 Best-of-N 可以获得超过 4 倍的计算效率；对于小模型已经具备一定成功率的问题，增加测试时计算甚至可能超过参数规模大 14 倍的模型。[Snell 等人的论文](https://arxiv.org/abs/2408.03314)

但对于最困难的问题，更强的基础模型依然重要。测试时计算不能凭空创造模型完全不具备的能力。

## 九、Archon：自动搜索推理时架构

不同模型、任务和预算所需要的最佳推理策略不同，人工设计很难覆盖庞大的组合空间。因此 Archon 将其建模为 Inference-Time Architecture Search。

它可以组合以下算子：

- Generator：生成候选答案；
- Fusion：融合多个候选；
- Critic：分析候选的问题；
- Revision：根据批评修改答案；
- Ranker：为候选排序；
- Verifier：验证答案；
- Unit Test Generator/Evaluator：生成并执行测试。

典型结构类似：

> 多模型生成 → 候选融合 → Critic 评价 → Revision 修正 → Ranker/Verifier 选择

Archon 的 ITAS 优化器会在给定以下条件后搜索最佳工作流：

- 可使用的模型集合；
- 最大 Token/计算预算；
- 目标数据集；
- 准确率与成本目标。

核心发现是：推理时工作流本身也可以被优化，不能只优化单个 Prompt 或选择单个最强模型。

最新版本论文报告，Archon 在指令遵循、推理和代码任务上，相对 o1、GPT-4o、Claude 3.5 Sonnet 等基线平均提高 15.1%，并推进准确率—Token 预算的 Pareto 前沿。[Archon 论文](https://arxiv.org/abs/2409.15254)  
视频中展示的数字约为 14.1%，差异主要来自论文版本更新。

## 十、对自进化 Agent 的启示

结合你关注的 Agent 评测和自进化体系，这节课可以抽象为下面的闭环：

$$
\text{生成多条轨迹}
\rightarrow
\text{执行与验证}
\rightarrow
\text{选择优质轨迹}
\rightarrow
\text{沉淀训练/Skill/Prompt数据}
\rightarrow
\text{更新系统}
\rightarrow
\text{重新评测}
$$

实际建设时最值得关注的是：

1. **先设计验证器，再扩大生成规模**  
   没有可靠验证器，生成 1000 条轨迹通常只是把选择问题放大。

2. **同时报告 pass@1、pass@k 和 verifier@k**  
   pass@k 衡量模型潜在能力；verifier@k 衡量系统能否找到正确候选；最终 pass@1 衡量用户真正得到的结果。

3. **将预算作为评测维度**  
   除准确率外，还要记录 Token、调用次数、延迟、模型成本和并行度。

4. **根据任务难度路由**  
   简单任务单次生成，中等任务 Best-of-N，困难任务进入反思/搜索流程，极难任务升级更强模型。

5. **把 Agent harness 看作推理时架构**  
   Generator、Critic、Judge、工具执行、回放、融合、停止条件，本质上都是可组合、可搜索的 inference-time operators。

## 最核心的三个结论

- **推理计算是独立于模型参数的能力扩展轴。**
- **重复采样暴露的是模型的潜在能力，验证器决定这种能力能否转化为实际效果。**
- **未来 Agent 自我改进的竞争重点，会从单纯生成更多轨迹，转向构建可靠验证、动态预算分配和可优化的推理时架构。**
